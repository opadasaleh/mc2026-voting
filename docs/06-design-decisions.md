# 06 — Design Decisions

Each entry records what we chose, the main alternatives, and why. They are numbered so other documents can refer to them (for example "D6").

| # | Decision | Alternatives considered | Why |
|---|---|---|---|
| D1 | **Laravel 13 API + Filament admin panel**, Next.js frontend built by a separate developer | One full-stack Next.js app; Node/Express API; Django | Laravel gives tokens (Sanctum), validation, rate limiting, encryption and migrations out of the box. Filament gives a complete, secure admin panel with MFA in a fraction of the time. A clean JSON API lets the frontend developer work in parallel against a written contract. |
| D2 | **Supabase Postgres (Frankfurt)** as the only data store | MySQL on the app server; Firebase; SQLite | Managed Postgres with backups and connection pooling, real constraints (`UNIQUE`, composite foreign keys, `CHECK`), `inet`/`jsonb` types, and no server to look after. Frankfurt is the closest EU region to Amman. We use Postgres only, not Supabase Auth or its client SDK, so the database could move to any Postgres. |
| D3 | **Multiple independent events**: every path is `/events/{slug}/…`, every token and admin page is bound to one event | Hard-code MC2026 | The Makerspace runs more than one event. Building it in from the start cost little and keeps events from leaking into each other. |
| D4 | **OTP confirmed again for each event** | Verify a phone once, forever | A token stolen or left on a borrowed phone cannot be reused at a later event; each event's verification state stands on its own. |
| D5 | **Phone number = visitor identity**, normalised to E.164, stored **encrypted + HMAC blind index** | Plain phone column; hash only | Visitors enter only name + phone (F5). E.164 stops one person registering `079…` and `+96279…` as two people. Encryption meets the privacy requirement while the HMAC still allows a unique index and fast lookup. A hash alone would make the outreach list (F14) impossible. |
| D6 | **On-site rule = venue Wi-Fi only (public IP allowlist)**; geofence removed | IP *or* GPS; IP *and* GPS; GPS only | The venue promised Wi-Fi covering the whole event for 1,000+ users. A public IP cannot be faked by the phone; a GPS position can, and it needs a permission prompt. Keeping only the strongest check is the fairest rule and the simplest to explain. Trade-off: a visitor who cannot join the Wi-Fi cannot vote; mitigated by signage, a clear "No access" page and live editing of IP ranges. |
| D7 | **Never rate-limit visitors by IP at the venue**; limit per phone and per token instead | Classic per-IP throttling | All 1,000 visitors share the venue's single public IP. Per-IP limits would lock everyone out at the busiest moment. Off-site IPs (already rejected by the gate) are still throttled per IP. |
| D8 | **The database enforces one vote per category** (`UNIQUE`) and same-event integrity (composite foreign keys); votes are immutable | Check in code only | Code checks can race under concurrent requests (two taps, retries). Constraints make double votes impossible, whatever the timing. |
| D9 | **Idempotent vote retries**: resending the same vote returns `200`, a different choice `409` | Always `409` on a duplicate | Phones on busy Wi-Fi drop responses. The frontend can safely retry and still show a confirmation. |
| D10 | **Votes cannot be changed** after casting | Allow changing until voting closes | Matches F2/F12 and keeps the audit story simple: every counted vote is the visitor's first and only choice for that category. |
| D11 | **Server-Sent Events** for the TV, with a 1 s results cache and streams that close after ~5 minutes | WebSockets (Laravel Reverb / Pusher); polling only | SSE is plain HTTP: no extra server, no sticky sessions, passes proxies, auto-reconnects in the browser. Full snapshots mean no catch-up logic. Closing streams periodically stops a PHP worker being held forever. Polling `GET /results` remains the fallback. |
| D12 | **Display tokens owned by the event**, read-only, shown once, expiring, revocable | Public results page; share an admin login on the TV | The brief asks for a protected results page. A token per screen is safer than an admin session on a public TV and can be revoked in one click. |
| D13 | **At most 3 categories per event; each exhibitor in exactly one category** | Exhibitor in several categories (spec F9 says "one or more") | Team decision, a deliberate deviation from F9: simpler for visitors (each exhibitor appears once) and for results. The limit is a config value (`MAX_CATEGORIES_PER_EVENT`), and the schema change back to many-to-many is small if needed. |
| D14 | **Deactivate instead of delete** for exhibitors with votes (soft delete; category locked once voted) | Hard delete | Removing an exhibitor must never silently remove votes from the totals. Their votes still appear in results and exports. |
| D15 | **Stateless app servers**: tokens instead of cookies for the API; sessions, cache, rate-limit counters and queue in Postgres; photos on object storage | File sessions/cache; Redis | Any instance can serve any request, so we can run two or more servers behind a load balancer and lose one without pausing voting. Postgres-backed drivers avoid adding Redis for a 1,000-user event; Redis is a drop-in later if load ever requires it ([08](08-scaling.md)). |
| D16 | **Supabase public API closed**: RLS on every table with no policies, `anon`/`authenticated` privileges revoked | Rely on keeping the anon key private | The anon key is designed to be public. Locking the tables makes the Laravel API the only access path, and a test fails if a new table forgets RLS. |
| D17 | **SMS behind an interface** (`SmsSender`) with a `log` driver | Call a provider SDK directly | CPF chooses the gateway later. Adding it is one class and one config value; development and demos work without sending real SMS. |
| D18 | **Admin login = username + password + required TOTP**, all admins see all events | Email login; per-event admin roles | Matches the brief ("username and password, MFA if possible") and the Makerspace team's size. Per-event roles can be added later through Filament's tenancy. |
| D19 | **All times stored in UTC** (`timestamptz`), shown in Asia/Amman in the admin panel | Local time in the database | No daylight-saving or server-timezone surprises. The API returns ISO-8601 UTC and `server_time`, so countdowns do not depend on the phone's clock. |
| D20 | **Tests run against a real Postgres in Docker, never Supabase** | SQLite in memory; test against Supabase | The constraints we depend on (`UNIQUE`, composite foreign keys, RLS, SQLSTATE codes) are Postgres features. A guard refuses to run tests against a Supabase host, so a test can never wipe live data. |
